# 인터랙티브 작품의 세로 영상 소스 제작

실제 웹 작품을 조작해 편집용 장면 소스와 전체 연결본을 만드는 절차다. 제목·회차·자막·음악을 붙이는 최종 릴스 편집과 구분한다. 작품별 구성, 자막, 채택한 수치와 결과 파일 위치는 Notion의 작품별 기록에 둔다.

## 1. 길이보다 행동과 반응을 먼저 정한다

각 장면에 **입력 → 반응 → 다음 동작을 위한 상태**를 적는다. 그리기라면 선을 긋는 동작뿐 아니라 생성된 대상이 움직이기 시작하는 모습까지 필요하다. 드래그라면 손을 놓은 뒤에도 선택 상태가 유지되는지 확인한다.

- 처음에 주요 상호작용을 보여주고, 이어서 작품의 중간 표현을 단계별로 보여줄 수 있다.
- 장면 순서와 조작을 정한 뒤 읽히는 데 필요한 시간을 준다. 전체 길이를 먼저 고정해 조작을 잘라내지 않는다.
- 설명 장면까지 요청받았다면 전체 연결본에도 모두 포함한다. 도입부 미리보기만 전달하고 완료로 처리하지 않는다.
- 장면 사이에 페이지를 다시 열거나 무작위 상태를 초기화하지 않는다. 같은 작품 상태에서 표현 모드만 전환한다.

## 2. 작품의 커서와 UI를 보존한다

기존 Chrome 창에서 현재 작품을 확인하고, 촬영용 탭의 화면 크기를 먼저 맞춘다. 세로 릴스 소스의 출력 프로필은 9:16, 1080×1920, 30fps를 사용할 수 있다. CSS 화면 크기, 기기 픽셀 비율, 실제 Canvas 크기와 출력 크기를 별도로 확인한다.

- 작품에 적용된 커서의 SVG·색·크기·외곽선·누름 효과를 재사용한다. 임의의 원형 포인터로 대체하지 않는다.
- 선택 상자, 조절 핸들, 크기 숫자는 조작을 설명하는 작품 UI다. 자막을 빼 달라는 요청을 작품 UI까지 숨기는 것으로 해석하지 않는다.
- 디버그 패널과 단계 선택 버튼 등 촬영 제어 UI는 출력에서 숨기되, 실제 조작 UI는 유지한다.
- Canvas 영상만 저장하면 DOM에 있는 커서·그리는 선·선택 UI가 빠진다. DOM까지 캡처하거나, 실제 SVG와 계산된 스타일·좌표·문구를 사용해 출력 Canvas에 합성한다.
- 합성하는 경우 실제 브라우저 스크린샷과 대조한다. 글꼴, 숫자, 핸들 위치, 누름 상태가 다르면 원본 UI를 그대로 담았다고 설명하지 않는다.

커서 표시를 위한 입력과 작품을 조작하는 입력이 함께 있을 때는 별도 포인터 ID로 구분한다. 표시용 입력이 실제 클릭이나 두 번째 드래그로 처리되지 않게 한다.

## 3. 마우스 이동에 가감속을 준다

일정한 속도의 직선 이동은 조작이 기계적으로 보이기 쉽다. 이동을 시작할 때 가속하고 목적지에 가까워질수록 감속하도록 진행률을 바꾼다. 다음은 정규화한 시간 `t`에 적용하는 cubic ease-in-out 예다. `t`는 시작에서 0, 도착에서 1이며, 반환값도 0에서 1로 증가한다.

```js
function easeInOutCubic(t) {
  return t < 0.5
    ? 4 * t * t * t
    : 1 - Math.pow(-2 * t + 2, 3) / 2;
}
```

각 프레임의 위치는 시작점과 도착점 사이를 이 진행률만큼 이동시킨 값이다. 가벼운 곡선 경로를 더할 수 있지만, 끝점에서는 편향이 0이 되어 실제 클릭 좌표에 도착해야 한다.

- 이동 시간은 이동 거리와 목표 속도를 기준으로 정한다. 모든 이동을 같은 시간으로 처리하지 않는다.
- 전체 커서 속도를 바꾸는 배율은 작품의 시뮬레이션 속도와 분리한다. 커서만 빨라져야 할 때 물체의 움직임까지 배속하지 않는다.
- 시간에 배율을 곱했다면 속도 배율은 그 역수다. ‘이동 시간 감소율’과 ‘속도 증가율’을 혼동하지 않는다.
- 핸들을 당기는 동작은 입력이 정확해야 하므로 과한 흔들림이나 끝점 오버슈트를 넣지 않는다.
- 클릭 전에 짧은 도착 시간을 둘 수 있지만, 모든 동작마다 긴 정지 구간을 만들지 않는다.

채택한 배율과 장면별 이동 시간은 작품별 기록에 남긴다. 한 작품에서 좋았던 속도를 모든 작품의 기본값으로 고정하지 않는다.

## 4. 손그림은 선과 속도를 함께 불규칙하게 만든다

정확히 닫힌 타원을 일정 간격으로 따라 그리면 사람이 그린 선처럼 보이지 않는다. 먼저 비대칭인 손그림 제어점을 준비하고, 제어점 사이를 부드럽게 연결한다. 그 위에 작은 위치 변화와 속도 차이를 더한다.

- 좌우·상하가 조금 다르고, 시작점과 끝점이 약간 어긋난 경로를 사용한다.
- 위치 변화는 선을 망가뜨리지 않는 작은 범위로 제한한다. 큰 무작위 흔들림을 매 프레임 독립적으로 넣지 않는다.
- 구간별로 진행 속도를 달리한다. 방향이 바뀌는 곳이나 선을 잇는 순간에 작은 머뭇거림을 줄 수 있다.
- 재촬영 비교가 필요하면 고정한 제어점과 재현 가능한 변화 패턴을 사용한다.
- 선을 그린 뒤 실제 작품이 해석한 결과를 확인한다. ‘그린 외곽선을 그대로 복제한다’는 식의 설명을 구현 확인 없이 붙이지 않는다.

## 5. 클릭 충돌과 선택 상태를 확인한다

정지 화면의 빈 곳도 커서가 도착할 때는 움직이는 대상이 차지할 수 있다. 클릭할 목적지를 고른 뒤, 입력 직전에 다시 확인한다.

| 장면 | 입력 전 확인 | 입력 후 확인 |
| --- | --- | --- |
| 더블클릭·파동 | 반응을 잘 보여줄 대상 무리 근처이면서 클릭 지점은 비어 있는가 | 첫 클릭과 두 번째 클릭 모두 다른 대상을 선택하지 않는가 |
| 크기 조절 | 대상 선택과 핸들 위치가 맞는가 | 요청한 방향으로만 크기가 바뀌고 숫자도 갱신되는가 |
| 드래그 | 핸들이 아닌 대상의 몸을 잡았는가 | 이동 후 손을 놓았는가, 선택이 계속 유지되는가 |
| 동작 재개 | 선택 해제가 필요한 작품인가 | 빈 곳을 바로 클릭한 뒤 선택 UI가 사라지고 대상이 다시 움직이는가 |

대상이 모인 곳은 ‘대상 위’와 다르다. 주변 대상 수·거리와 클릭 가능한 빈 영역을 함께 평가한다. 입력 후 상태가 예상과 다르면 그 테이크를 완료로 처리하지 않는다.

대상 탐색을 위해 화면 전체를 훑거나 파일을 저장하는 작업은 실시간 녹화에서 지연을 만들 수 있다. 탐색과 저장이 재생을 막지 않게 하며, 긴 정지 화면을 편집으로 숨기는 데 의존하지 않는다.

## 6. 실시간 녹화가 끊기면 프레임 단위로 저장한다

브라우저가 가려지거나 작업이 길어질 때 실시간 녹화의 프레임이 불규칙해질 수 있다. 이때는 **실제 작품을 한 프레임씩 진행 → 렌더링 → UI 합성 → 인코딩**하는 촬영용 래퍼를 사용할 수 있다. 이는 실시간 화면 녹화와 다른 방식이므로 제작 기록에 구분해서 남긴다.

1. 작품 모듈을 불러오기 전에 촬영용 페이지에 시계와 프레임 진행 함수를 준비한다. 제품 코드의 동작을 영구 변경하지 않는다.
2. 한 프레임마다 목표 fps에 해당하는 시간만큼 작품을 진행한다. 입력 이벤트도 같은 시계에 맞춘다.
3. 렌더링 직후 WebGL Canvas를 출력 Canvas로 복사한다. 브라우저가 버퍼를 비운 뒤 읽지 않도록 같은 프레임에서 처리한다.
4. 해당 순간의 커서와 DOM UI를 함께 담는다. CSS 애니메이션과 Web Animations는 JavaScript 시계만 바꾼다고 함께 진행되지 않으므로 별도로 동기화하거나 상태를 명시적으로 재현한다.
5. `VideoFrame`의 timestamp는 프레임 번호에 대응시키고, `VideoEncoder`에 순서대로 전달한다. 프레임을 넘긴 뒤 `VideoFrame.close()`를 호출한다.
6. 인코딩 대기열이 커지면 다음 프레임 생성을 잠시 기다린다. 벽시계 시간이 늘어도 출력 영상의 시간 간격은 일정하게 유지한다.
7. 끝에서 `flush()`를 기다리고 오류와 입력·출력 프레임 수를 확인한다. VP9 청크를 IVF로 묶는다면 헤더의 크기·fps·프레임 수와 각 프레임 timestamp를 일치시킨다.
8. 편집용 MP4로 변환하고 크기·fps·길이·전체 프레임 수를 확인한다.

시간은 한 번만 프레임 수로 환산한다. 예를 들어 fps가 `F`일 때 입력 시간 `durationMs`의 프레임 수는 `ceil(durationMs * F / 1000)`이고, 인코더에 줄 프레임 `i`의 timestamp는 `round(i * 1000000 / F)` 마이크로초다. 속도 배율은 프레임 수로 환산하기 전에 적용한다.

이 방법은 JavaScript 시계로 진행 가능한 작품에 적합하다. 외부 영상·오디오·네트워크 응답·CSS 타임라인까지 포함된 작품은 각 시간원을 따로 맞춰야 한다. 촬영용 `setPointerCapture` 대체나 입력 우회가 필요하면 래퍼에 한정하고, 실제 선택·드래그 결과가 정상 입력과 같은지 확인한다.

## 7. 장면 경계와 검증

각 장면 시작을 프레임 번호로 기록한다. 전체 연결본에서 장면을 나눌 때는 `[시작 프레임, 다음 장면 시작 프레임)` 범위를 사용한다. 모든 클립의 프레임 수를 합한 값이 전체 소스의 프레임 수와 같아야 한다.

- 정확한 경계가 필요하면 프레임 단위 `trim` 후 각 클립의 시간을 0부터 시작시켜 다시 인코딩한다. 키프레임 위치에 의존하는 단순 스트림 복사로 경계를 맞췄다고 가정하지 않는다.
- 출력 해상도, 실제 fps, 클립별 프레임 수와 전체 길이를 검사한다.
- 문제 구간의 앞·중간·뒤 프레임을 나란히 보고 커서와 주변 작품이 계속 움직이는지 확인한다.
- 프레임 해시는 완전히 같은 프레임이 반복되는지 찾는 보조 수단이다. 모든 해시가 달라도 움직임이 자연스럽다는 증명은 아니다.
- 화면 대부분이 단색이거나 움직임이 작은 작품은 자동 `freezedetect`가 정상 장면도 정지로 분류할 수 있다. 검출값만으로 성공·실패를 결정하지 않는다.
- 선택된 한 대상이 멈추는 작품의 정상 동작과 화면 전체의 재생 정지를 구분한다.
- 실제 재생으로 속도·easing·클릭 위치·선택 해제·설명 단계 전환을 확인한다. 프레임 검사만으로 사용자 검토를 대체하지 않는다.

## 8. 전달과 보관

- **전체 연결본**: 조작 장면부터 설명 단계와 마지막 완성 화면까지 포함한다.
- **장면별 소스**: 같은 테이크를 순서대로 나누고 이름에 순서를 붙인다.
- **재제작 자료**: 촬영 래퍼, 입력 동선, 인코딩·분할 방법을 최종 소스와 연결해 보관한다. 특정 컴퓨터의 절대 경로와 포트는 실행 전에 확인한다.
- **작품별 기록**: 최종 파일 위치, 채택한 속도·easing·조작 기준, 사용자 검토 상태를 Notion에 남긴다. 로컬 경로를 Notion 첨부나 공개 다운로드 주소처럼 표시하지 않는다.

영상·ZIP·QA 비교 이미지·프레임별 측정 로그는 Git에 넣지 않는다. 임시 검증 파일은 작업 후 정리하고, 공통 절차는 이 가이드에, 작품별 운영 기록은 Notion에 유지한다. 기존 정지형 공유 이미지 제작은 [소셜 공유 이미지 제작](./social-share-images.md)을 따른다.
