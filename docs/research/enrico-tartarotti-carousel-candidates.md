# 카드뉴스 후보 · 익숙한 기능의 보이지 않는 작동

조사일: 2026-10-25 · 출발점: [Enrico Tartarotti](https://www.youtube.com/@enricotartarotti) · [전체 111편 조사](./enrico-tartarotti-channel-research.md)

역사보다 현재의 동작·감각·판단을 우선한 36개 후보입니다. 아래 문구는 소재를 식별하는 가안이며 확정 표지나 원고가 아닙니다. 영상 하나를 그대로 요약하기보다 그 안의 작은 문제 하나를 독립적인 이야기로 발전시키는 목록입니다. 같은 소재의 긴 영상·쇼츠는 합쳤습니다. 이미 제작한 Figma 복붙과 Pull to Refresh는 제외했습니다.

영상 링크의 시간은 자막에서 해당 설명을 찾기 시작할 위치입니다. 자동 자막 기준이므로 실제 장면을 캡처할 때 앞뒤를 확인합니다. ‘공식 보강’은 아래 좁은 범위의 원리를 확인했다는 뜻이며, 영상의 모든 수치·회사 의도·현재 앱 동작까지 검증했다는 뜻은 아닙니다. 나머지는 영상 근거가 있는 제작 후보로, 적힌 확인 항목을 해결한 뒤 원고로 확정합니다.

## A · 먼저 제작해 볼 12개

### 01 · 내가 누른 글자와 키보드가 고른 글자는 다를 수 있다

- 핵심: 화면의 자판 경계와 입력 판정은 별개입니다. 터치 위치와 문맥의 가능성을 함께 해석하고, 사용자의 터치 습관을 반영할 수 있습니다.
- 전개·화면: 자판을 빗나간 터치 → 그래도 맞게 나온 단어 → 터치 분포와 후보 확률을 겹친 직접 제작 도식. 사용자가 제안한 방향과 가장 가깝습니다.
- 영상: [키보드 설명 00:00](https://www.youtube.com/watch?v=rAVV4kAYlI8&t=0s), [해당 쇼츠](https://www.youtube.com/watch?v=ylFXKeTVbec).
- 공식 보강: [Gboard의 공간 모델](https://research.google/blog/the-machine-intelligence-behind-gboard/), [개인별 공간 모델 연구](https://research.google/pubs/spatial-model-personalization-in-gboard/). Gboard 근거로 모든 최신 iOS 키의 사각형이 동일하게 바뀐다고 단정하지 않습니다. 언어·키보드별 차이도 확인합니다.

### 02 · 메뉴가 안 닫히는 이유는 보이지 않는 삼각형이다

- 제작 상태: 본편 12장 초안 제작. [원고·출처 기록](https://app.notion.com/p/405a89f7e31a81b59536fe23259e27f1) · [피그마](https://www.figma.com/design/m9xgjiza93wsgwqZdPhW7g/Page?node-id=1154-199). 게시 전이며, 원고는 Notion에서 관리합니다.
- 핵심: 하위 메뉴로 대각선 이동할 때 다른 행을 스치더라도 의도를 추정해 메뉴를 유지하는 기법이 있습니다.
- 전개·화면: 자꾸 닫히는 메뉴 시연 → 포인터 이동 경로 → 메뉴까지 연결한 삼각 영역 → 적용 전후 비교. 카드 한 장마다 원인이 눈에 보입니다.
- 영상: [Notion 팀 인터뷰 15:00 부근](https://www.youtube.com/watch?v=b00sgRR_Vc0&t=900s).
- 확인: [Ben Kamens의 menu-aim 구현](https://github.com/kamens/jQuery-menu-aim)을 출발점으로 실제 코드를 읽고 직접 재현합니다. 모든 메뉴가 이 알고리즘을 쓴다는 표현은 피합니다.

### 03 · 버튼은 누르는 순간보다 떼는 순간이 더 복잡하다

- 핵심: 눌림·손을 뗌·영역 밖 이동·재진입·허용 오차가 버튼 하나의 동작을 구성합니다.
- 전개·화면: 눌렀다가 손가락을 밖으로 빼면? → 돌아오면? → 즉시 실행하는 버튼과 비교 → 상태별 직접 시연. 독자가 바로 따라 해 볼 수 있습니다.
- 영상: [버튼 상태 01:15 부근](https://www.youtube.com/watch?v=rAVV4kAYlI8&t=75s), [요약 쇼츠](https://www.youtube.com/watch?v=BGWnz8FVS1U).
- 확인: 일반적인 버튼과 키보드·게임·길게 누르기 등 다른 입력 정책을 분리합니다. touch-up 규칙을 모든 버튼의 필수 동작으로 일반화하지 않습니다.

### 04 · 지도는 축소할 때 글자도 같이 줄이지 않는다

- 핵심: 지도와 달리 라벨은 읽을 수 있는 크기를 유지해야 하므로, 충돌 검사와 배치·생략 규칙이 필요합니다.
- 전개·화면: 같은 지역의 확대·축소 캡처 → 사라지는 이름 표시 → 라벨 경계 상자와 충돌 도식. 도로·장소 정보가 화면에 남는 과정을 보여줍니다.
- 영상: [지도 설명 09:30](https://www.youtube.com/watch?v=qSQZ8B-2nU0&t=570s).
- 공식 보강: [Mapbox 라벨 배치](https://docs.mapbox.com/help/dive-deeper/optimize-map-label-placement/). 이는 지도 렌더러의 일반 문제를 확인하는 자료이며 Google Maps의 개인화 순위를 증명하지 않습니다. Google의 특정 우선순위 주장은 별도 확인합니다.

### 05 · 누르기도 전에 다음 페이지가 열려 있다

- 핵심: 링크에 관심을 보이는 행동을 신호로, 이동 전에 데이터를 가져오거나 페이지를 미리 렌더링할 수 있습니다.
- 전개·화면: 클릭 전부터 돌아가던 타이머 → 포인터 접근·대기 → 네트워크 요청 → 빠른 전환. ‘빠른 서버’ 외의 속도 개선 방법을 보여줍니다.
- 영상: [선행 로딩 설명 12:00 부근](https://www.youtube.com/watch?v=qSQZ8B-2nU0&t=720s).
- 공식 보강: [Chrome prerender 문서](https://developer.chrome.com/docs/web-platform/prerender-pages). prefetch와 prerender를 구분하고, 적용 사이트·정책에 따라 실행된다는 범위를 붙입니다.

### 06 · 화면에는 저장됐는데 서버는 아직 모를 수 있다

- 핵심: 작업을 화면에 먼저 반영하고 전송 큐에서 서버와 맞추면 기다림이 줄어듭니다. 대신 실패·재시도·충돌 처리가 필요합니다.
- 전개·화면: 댓글 즉시 추가 → 네트워크 끊기 → 전송 대기 → 재연결 또는 실패 복구. ‘즉시 반응’의 비용을 구체적으로 설명할 수 있습니다.
- 영상: [작업 큐 설명 01:00](https://www.youtube.com/watch?v=XqhduyTnEM8&t=60s).
- 확인: optimistic UI, 로컬 저장, 서버 저장 완료는 서로 다릅니다. 저자의 Flask 구현과 Notion·Figma의 실제 저장 보장을 같은 것으로 설명하지 않습니다.

### 07 · 이모지 한 글자는 컴퓨터에겐 여러 글자일 수 있다

- 핵심: 피부색·직업·가족 등 일부 이모지는 여러 코드 포인트와 결합 규칙으로 만들어집니다. 보이는 글자 수와 데이터 길이는 다를 수 있습니다.
- 전개·화면: 이모지 하나 분해 → 결합 문자 표시 → 기기별 렌더링 → 글자 수·커서 처리의 차이. 짧은 코드나 직접 만든 분해 도식으로 설명 가능합니다.
- 영상: [텍스트 영상 00:00](https://www.youtube.com/watch?v=7DN3Ectm6UY&t=0s).
- 공식 보강: [Unicode Emoji 표준](https://www.unicode.org/reports/tr51/). ‘모든 이모지는 여러 문자’라는 표현을 피하고 grapheme cluster와 code point를 구분합니다.

### 08 · 셔플은 왜 방금 들은 곡을 기억할까?

- 핵심: 진짜 무작위에도 연속·반복이 생깁니다. 현재 Spotify의 Fewer Repeats는 여러 무작위 순서를 만들고 최근 재생 기록을 기준으로 더 신선한 순서를 고릅니다. Standard와는 정책이 다릅니다.
- 전개·화면: 완전 무작위 재생열 → 같은 가수의 연속 → 반복을 줄인 재생열 → 사용자가 기대하는 무작위와 비교.
- 영상: [셔플 단독 영상](https://www.youtube.com/watch?v=NhAIA-o7f4M).
- 공식 보강: [Spotify의 2025년 설명](https://engineering.atspotify.com/2025/11/shuffle-making-random-feel-more-human), [현재 셔플 안내](https://support.spotify.com/us/article/shuffle-play/). 2021년 영상의 방식을 현재 전부에 적용하지 않습니다. Standard·Fewer Repeats·Smart Shuffle을 구분합니다.

### 09 · 탭인지 스크롤인지, 휴대폰도 잠깐 판단한다

- 핵심: 손가락을 댄 뒤의 시간·이동 거리로 입력 의도를 구분합니다. 같은 터치가 버튼 실행과 화면 이동 중 무엇이 될지 아직 정해지지 않은 순간이 있습니다.
- 전개·화면: 버튼 위에서 살짝 이동하는 손가락 → 좌표·시간 표시 → 거리 임계값 안팎 비교. 독자가 실제로 실험해 보기 좋습니다.
- 영상: [입력 판정 04:16](https://www.youtube.com/watch?v=7EVZpW9Rdwk&t=256s).
- 공식 보강: [Android ViewConfiguration](https://developer.android.com/reference/android/view/ViewConfiguration). 영상의 100ms·8dp를 모든 기기·앱의 고정값으로 쓰지 않습니다.

### 10 · 숫자가 바뀌는데 타이머의 콜론은 왜 안 흔들릴까?

- 핵심: 숫자마다 폭이 다르면 시간·카운터가 바뀔 때 주변 글자가 움직입니다. 숫자 폭을 맞추는 기능이 이를 막습니다.
- 전개·화면: 일반 비례 숫자와 tabular 숫자의 타이머를 나란히 재생 → 콜론 위치 겹치기 → Notion 숫자 UI와 직접 제작 예시.
- 영상: [텍스트 07:00](https://www.youtube.com/watch?v=7DN3Ectm6UY&t=420s), [Notion 숫자 정렬 12:00 부근](https://www.youtube.com/watch?v=b00sgRR_Vc0&t=720s).
- 확인: 전체 글꼴이 monospace인 경우와 비례 글꼴의 tabular numerals를 구분합니다. 현재 Notion 화면도 다시 비교합니다.

### 11 · 휴대폰 음량 50%는 소리의 절반일까?

- 핵심: 슬라이더 위치·물리적 출력·사람이 느끼는 크기는 같은 비율로 움직이지 않습니다.
- 전개·화면: 같은 간격으로 올린 슬라이더 → 실제 출력 곡선과 지각 비교 → 작은 단계가 중요한 이유. 그래프가 자연스럽게 필요한 소재입니다.
- 영상: [음량 설명 00:00](https://www.youtube.com/watch?v=7nnyv4yJGJc&t=0s), [쇼츠](https://www.youtube.com/watch?v=fBdxtU6JN6M).
- 확인: 진폭·음향 파워·dB·주관적 음량을 혼용하지 않습니다. ‘절반’이라는 수치와 각 OS의 실제 매핑은 별도 측정·공식 자료로 확인한 뒤 확정합니다.

### 12 · 앱이 아이콘에서 커지는 건 로딩 시간을 벌기 위해서이기도 하다

- 핵심: 시작 애니메이션은 앱의 위치를 알려주는 동시에 초기 화면 준비 시간을 연결합니다.
- 전개·화면: 앱 실행을 느리게 재생 → 아이콘·launch screen·실제 첫 프레임 분리 → 다른 곳에서 튀어나오는 대조 시연.
- 영상: [공간적 연결 00:00](https://www.youtube.com/watch?v=z3Lo5QT7nME&t=0s), [로딩과 launch screen 14:10 부근](https://www.youtube.com/watch?v=z3Lo5QT7nME&t=850s).
- 확인: Apple의 최신 launch screen 가이드·WWDC 자료로 범위를 보강합니다. 애니메이션 전체의 목적을 로딩 은폐 하나로 축소하지 않습니다.

## B · 시각 자료와 재현을 준비하면 좋은 16개

### 13 · 배터리 37%는 누가 세고 있을까?

- 핵심: 잔량은 배터리 안의 물을 눈금처럼 읽는 값이 아니라 측정과 모델을 결합한 추정입니다.
- 시각 자료: 전압만 읽기 → 온도·부하 변화 → 입출력 전하 추적 → 노화 보정의 단계별 도식.
- 영상: [배터리 잔량 00:00](https://www.youtube.com/watch?v=-YVtZV4DjCE&t=0s).
- 확인: 연료 게이지 제조사 자료로 전압·쿨롱 카운팅·모델 기반 추정을 보강합니다. 모든 휴대폰이 ‘수년간의 사용 기록을 ML로 분석’한다는 영상 표현은 검증 전 제외합니다.

### 14 · 입력도 끝나기 전에 ‘잘못된 이메일’이라고 하면 왜 짜증 날까?

- 핵심: 형식 검증은 규칙만큼 실행 시점이 중요합니다. 입력 도중·포커스 이탈·전송 직전의 피드백이 다른 경험을 만듭니다.
- 시각 자료: 첫 글자부터 빨간 이메일 입력창 vs 입력을 마친 뒤 안내하는 창. 비밀번호 조건 안내와도 비교합니다.
- 영상: [검증 상태 04:00 부근](https://www.youtube.com/watch?v=qSQZ8B-2nU0&t=240s).
- 확인: 접근성·보조기기 알림과 사용자 실험을 보강합니다. 이메일은 언제나 blur, 비밀번호는 언제나 즉시라는 절대 규칙으로 쓰지 않습니다.

### 15 · 체크박스를 빗나갔는데도 체크가 된다

- 핵심: 보이는 작은 체크박스와 실제 클릭할 수 있는 범위가 다를 수 있습니다.
- 시각 자료: 포인터 좌표와 체크박스·행의 실제 판정 범위 겹치기 → 작은 목표를 누를 때의 오차 비교.
- 영상: [Notion 도입부](https://www.youtube.com/watch?v=b00sgRR_Vc0&t=0s).
- 확인: 현재 Notion에서 어느 영역까지 동작하는지 직접 기록하고, 전체 행 label 연결과 별도 hit target 확장을 구분합니다.

### 16 · 방향키로 위아래를 오가려면 이전 위치를 기억해야 한다

- 핵심: 글자 폭과 줄 길이가 다르기 때문에 단순히 n번째 문자로 이동하면 커서가 옆으로 밀립니다. 목표 가로 위치를 유지하는 정책이 필요합니다.
- 시각 자료: WWW·iii와 짧은 줄이 섞인 문단 → 위·아래 키 이동 → 목표 x좌표를 표시한 도식.
- 영상: [커서 설명 01:30](https://www.youtube.com/watch?v=-YVtZV4DjCE&t=90s), [텍스트 심화](https://www.youtube.com/watch?v=7DN3Ectm6UY&t=330s).
- 확인: 에디터마다 다른 caret 정책, RTL·합자·결합 문자를 분리합니다. 원래 위치를 항상 기억한다는 식으로 단정하지 않습니다.

### 17 · 같은 글꼴인데 Windows와 Mac에서 왜 다르게 보일까?
